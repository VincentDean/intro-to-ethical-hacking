TL
Executive TL;DR
The whole week, explained like you have thirty seconds
  • What is this? Students break into a website on purpose, but it is a legal practice website built just for this.
  • Why bother? Real websites get hacked because of small, sloppy mistakes. Students learn to spot those mistakes before a criminal does.
  • Is it dangerous? No. It is the same idea as a locked practice room. Nobody touches a real company's website.
  • What do they do all day? Solve one small puzzle at a time. Each solved puzzle unlocks the next, harder one. Eleven puzzles this week.
  • What tools do they need? A web browser. Nothing more. No special software, no coding required.
  • What do they walk away with? A working sense of how websites get broken into, and why that matters for anyone who runs one.

00
Authorization, Ethics & Team Structure
Read this before you touch a single level
⚠
Natas is a legal practice range: stay inside it

OverTheWire's Natas game lives at natas.overthewire.org and exists specifically for the public to practice web exploitation, legally and safely. You are authorized to attack the Natas levels and only the Natas levels. Never point any technique from this unit at a site you do not own or have explicit written permission to test. This is a graded shift from prior weeks: Natas needs live internet access, unlike the air-gapped AuraLab labs you have used before.

Natas is your training range for the same categories of bugs (leaked secrets, weak cookies, sloppy file handling, unfiltered input) that a sloppy web developer could ship into any real production site.

ℹ
The Feynman rule

No team submits a level's password until at least one member can explain, in their own words and without reading off a screen, why the exploit worked. Guessing your way to a password is not passing the level. Understanding it is.

01
What Is Natas?
The login pattern you will use for every single level

Natas is OverTheWire's web-exploitation war game. Each level is its own small, deliberately broken website. Your job is to find the flaw on that page and recover a password. That password logs you into the next level, where the flaw is different and usually harder.

URL pattern: http://natasN.natas.labs.overthewire.org
Username: natasN
Password: the password you recovered from level N-1
  • Level 0 is the only exception: it starts open. Username natas0, password natas0.
  • Solving level N reveals the password for level N+1, which you then use to log into natasN+1.
  • Your browser will prompt for HTTP Basic Authentication. Enter the username and password there.
  • Keep a running password log (see the LAB section) so your team never loses a credential mid-class.
02
Core Browser Skills
Four skills carry you through every level this week
View Source (Ctrl+U)
Shows the raw HTML the server sent you, including comments and hidden fields the rendered page hides.
DevTools (F12)
Elements (live DOM), Network (every request and response), Application (cookies and storage), Console (run JavaScript).
Editing HTTP requests
Read and change headers and cookies before a request is sent. Burp Suite works here too, but DevTools alone is enough for this unit.
Manual URL exploration
Type paths directly into the address bar. Check robots.txt and try guessing directories a page links to but does not show.
✓
Every level this week uses one or more of these four skills

You will not need a scripting language, an exploit framework, or anything beyond a browser and a login form. Web exploitation at this level is mostly close reading.

03
Key Vocabulary
Words you need to know before Day 1
TermDefinition
HTML sourceThe raw markup a server sends before the browser renders it into a page, comments and hidden values live here.
HTTP headerA key-value line sent with every request or response, such as Referer or Content-Type, that carries metadata rather than page content.
CookieA small piece of data the server asks your browser to store and send back on every later request, often used to track login state.
robots.txtA plain-text file at a site's root that tells search engine crawlers which paths not to index. It does not block a human from visiting those paths.
Directory listingA server auto-generated page showing every file in a folder, exposed when a folder has no index page and listing is not disabled.
Local File Inclusion (LFI)A vulnerability where user input controls which file a server reads and displays, letting an attacker request files outside the intended folder.
Encoding vs. encryptionEncoding (Base64, hex, string reversal) is reversible by anyone who knows the method, it hides nothing from an attacker. Encryption requires a secret key to reverse.
Command injectionA vulnerability where user input is passed unsanitized into a system shell command, letting an attacker run their own commands.
Path traversalUsing sequences like ../ or an absolute path to move outside a web application's intended directory and reach other files on the server.

D1
Day 1: Recon and Reading the Page (Levels 0-3)
Source, DevTools, directory listings, and robots.txt
▾
Objectives
  • Log into Natas using the natasN / password pattern
  • Read raw HTML source with View Source and DevTools
  • Browse an exposed directory and read a robots.txt file to find a hidden path
Warm-Up (Do Now)
  • On paper or in your notes: what is the difference between what you see rendered on a webpage and what the server actually sent? Write one sentence.
  • Navigate to natas0.natas.labs.overthewire.org and log in with natas0 / natas0.
Introduction

Every web page a developer ships can leak information they never intended a visitor to see: a comment left in during testing, a config file that was never removed, a folder that was supposed to be private. Bug bounty hunters and penetration testers start almost every engagement this way, checking source code and exposed paths before they try anything more advanced. It costs nothing and it works far more often than you would expect.

Guided / Independent Practice
  • Teacher models level 0 on the projector: open View Source, find the comment, log into natas1 with the recovered password.
  • Teams take over levels 1 through 3 independently, using the same View Source / DevTools approach.
  • Level 2 hint: an image is loading from somewhere. Where does that path lead if you visit it directly?
  • Level 3 hint: search engines are told to stay out of certain folders. That file is public.
D2
Day 2: HTTP Headers and Cookies (Levels 4-5)
Editing what your browser tells the server about itself
▾
Objectives
  • Explain what an HTTP header is and read one in the DevTools Network tab
  • Modify a request header to satisfy a server-side check
  • Read and edit a cookie's value in DevTools Application tab
Warm-Up (Do Now)
  • Open DevTools on any website, click the Network tab, reload the page, and click one request. List three headers you see.
  • Recover yesterday's stopping point and confirm your password log is current.
Introduction

Every request your browser sends carries headers describing where the request came from, what browser sent it, and whether you are logged in. A web application that trusts a header or a cookie without verifying it server-side is trusting something the visitor fully controls. This is one of the most common real-world web flaws, and it is why professionals treat client-supplied data as untrustworthy by default.

Guided / Independent Practice
  • Teacher models on level 4: opens the Network tab, resends the request with an edited Referer header, shows the page unlock.
  • Teams complete level 4 independently, then move to level 5 with less guidance.
  • Level 5 hint: the page says you are not logged in. Somewhere, something is tracking that state, and you can see it.
D3
Day 3: Exposed Files and Local File Inclusion (Levels 6-7)
When a server will read back any file you name
▾
Objectives
  • Locate a server-side include file that is directly reachable by URL
  • Define Local File Inclusion in their own words
  • Use a URL parameter to make a server read a file it was not meant to serve
Warm-Up (Do Now)
  • Quick write: if a webpage's source mentions it is loading another file to build the page, what happens if you visit that file's path directly?
Introduction

Web developers often break a site into pieces and have one file pull in another. If that included file sits inside the public web folder, anyone can request it directly. Local File Inclusion takes this further: when a URL parameter picks which file to load, an attacker can point it somewhere the developer never intended, including files completely outside the website itself. This is a serious, real-world vulnerability class, not just a training exercise.

Guided / Independent Practice
  • Teacher models level 6: shows the source referencing an included file, then requests that file's path directly to read its contents.
  • Teams work level 6 independently with the source-reading skills from Day 1.
  • Teams then attempt level 7, where a URL parameter chooses which page to display.
  • Level 7 hint: if a parameter controls which file loads, what happens if you point it at a file on the server that has nothing to do with this website?
D4
Day 4: Encoding and Command Injection (Levels 8-9)
Reversing a disguised secret, then breaking out of a shell command
▾
Objectives
  • Distinguish encoding from encryption and explain why encoding alone is not security
  • Reverse a chain of encoding transformations by hand or with online decoder tools
  • Define command injection and use it to run an unintended command on a target
Warm-Up (Do Now)
  • Quick poll: is Base64 encryption? Defend your answer in one sentence before the class discusses it together.
Introduction

A surprising number of applications, real ones included, mistake encoding for security. Base64, hex, and string reversal all look unreadable at a glance, but every one of them can be undone by anyone who recognizes the pattern. Command injection is a different and more serious mistake: when an application builds a shell command out of user input without cleaning it first, the user can smuggle in an entirely separate command of their own.

Guided / Independent Practice
  • Teacher models level 8: identifies the encoding functions in the source, reverses them in the correct order, and shows the recovered password.
  • Teams complete level 8 independently, documenting each step of the reversal in their notes.
  • Teacher briefly models level 9's form, showing how a normal search term gets passed to a command behind the scenes.
  • Teams attempt level 9, testing what a search-style input field actually does with unexpected characters.
  • Level 9 hint: the form runs a search tool against a file. What if your input told the shell to run a second, unrelated command right after?
D5
Day 5: Filter Bypass (Level 10) and Team Audit Summary
Getting past a character filter, then writing up the week
▾
Objectives
  • Explain why blocking specific characters does not fully close a command injection vulnerability
  • Bypass a character filter to complete level 10
  • Produce a team audit-summary write-up covering the week's findings (summative)
Warm-Up (Do Now)
  • Recall level 9's payload. If a developer blocked the characters ;, |, and &, would your exact payload from Thursday still work? Predict yes or no and why.
Introduction

Blocklisting specific characters is one of the most common, and most commonly broken, attempts at fixing an injection vulnerability. It treats the symptom instead of the root cause: the underlying command is still being built from unsanitized input. A tool that takes a filename and a second filename can sometimes be tricked into treating extra input as a second target, with no blocked characters required at all.

Guided / Independent Practice
  • Teacher models the filter itself on level 10, showing that the semicolon, pipe, and ampersand payload from level 9 now fails.
  • Teams work level 10 independently, testing how the underlying search tool can be pointed at a second file without any of the blocked characters.
  • Hint: the tool searches a file for a pattern. What if part of your input was not a search pattern at all, but a second filename?
  • Remaining time: teams draft their team audit-summary write-up (see Deliverable below).
✓
Summative deliverable, Team Audit Summary

For each level your team completed (0 through 10), write one short paragraph: the vulnerability category, how you found it, and the one fix a real developer should make to close it. This write-up is graded, not the raw passwords.
